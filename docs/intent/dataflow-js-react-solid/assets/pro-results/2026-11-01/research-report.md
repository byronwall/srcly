**Recommended decision.** Build a correctness-first shared value-transfer and proof contract, a real JavaScript project-admission path, and separate shippable vanilla JavaScript, React, and SolidJS tracks. Correct the existing rules that conflate receiver mutation, callback returns, callable identity, state updates, and asynchronous result fields before adding more API names. Use exact semantic fixtures, forbidden-path assertions, and differential/metamorphic tests as the main evidence. Keep PR #308's offline observation packets as an optional, bounded research comparison; retain them only when they change a justified review verdict beyond those tests. The implementation plan continues through native language rules, React 19 behavior, and Solid resources/props/stores/ownership, without a Solid-only pilot gate.

### Five different questions a flow edge might answer

| Claim | Meaning and limit |
| --- | --- |
| Static may-flow | A value may influence a destination under the analysis abstraction and stated conditions. A branch that did not execute in one run can remain a valid possible path. |
| Value derivation | Output is computed from input: a boolean selector, string transform, or copied property. This does not establish reference equality. |
| Reference identity | Two values are the same object/function reference in the stated context. A new container may preserve element identities while changing its own identity. |
| Taint propagation | Influence under a chosen source/sink/sanitizer policy. This is usually broader than exact value transfer and is not a universal equality relation. |
| Runtime execution | An event happened in one version, environment, input, action sequence, and observation window. It neither covers unexecuted alternatives nor proves a model for every program. |

Srcly already separates relation status from proof basis: `framework-state` and `standard-library` are **modelled** strengths even when a relation's status is `proven`. That distinction must be preserved. Conversely, an intentionally conservative state/provider union is not automatically an invalid may-flow merely because one execution selected one value. The audit targets definite channel contradictions, missing admissible programs, false exactness, and unsupported proof upgrades; it does not demand a complete scheduler or heap analysis. See [`kinds.ts`, proof traits](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/srcly/kinds.ts#L134-L205).

### Five highest-value vanilla gaps / risky claims

1. **Native generic semantics are overproved (J06–J08).** Correct receiver effects and callback signatures/returns before expanding standard-library green counts. The rule is more dangerous with unannotated JavaScript because `any` and compatible primitives remove the type separation used in existing examples. This is a source-backed rule defect; the precise projected graph is an experiment outcome, not already measured.
2. **Actual JS has first-mile access barriers and a misleading coverage denominator (J01–J05).** jsconfig-only, no-config, loose JS and `.mjs` roots need a first-class path. Strict TS success says little about these. Admission is a separate milestone and can ship without broader modeling if capability labels stay honest.
3. **Promise completion channels and ignored callback returns are conflated (J08).** Errors/finalizers drive everyday JS control flow. Add explicit fulfilled/rejected/settled channels and nonvalue callbacks; do not let a `reject(secret)` relation look like a successful `await` value, or a `finally` return replace an earlier fulfilled object.
4. **State storage lacks enough receiver/key identity and write semantics (J07/J10/J11).** Distinct class instances and Map keys may cross; setters and computed writes miss invocation/store paths. The existing map-cache fix remains useful but too coarse to prove values reached the specific requested read.
5. **Browser boundaries are classified from discarded syntax rather than the host operation (J12/J16).** A `querySelector` read becoming “browser write” is a wrong endpoint, not just missing coverage. Event identity and cancellation should be explicit may-callback relationships with lifecycle uncertainty. This materially affects vanilla DOM code and the framework tracks' event/effect internals.

Call/apply/bind and constructor functions are the next language gap after those five; they are substantive, but foundational wrong-proof fixes and project admission reach more users sooner. Full proxy/reflect/eval completeness is not a tractable immediate goal. Explicit unknowns are better than invented target identity.

**Additional inspected control:** `library-callbacks.tsx` currently excludes the object-element array from a numeric reduce accumulator by type compatibility. Add a two-iteration recurrence case: later accumulators may derive from earlier item fields. Existing `object-calls.tsx` already contains a two-factory negative, but permits stopping at the shared getter return; retain it while adding receiver-state controls. Native array counterexamples assume unmodified native methods on ordinary arrays; user overrides/species/getter/proxy effects remain separate applicability conditions.

## Question 2 — What srcly currently claims or measures too strongly

### SH-F1. Generic library recognition is being used as a behavioral proof

**Source fact.** `libraryProof` assigns `standard-library` / `proven` whenever the callee is recognized as a standard-library declaration. `connectExternalCall` infers receiver writes from a discarded result, while `connectExternalCallbacks` uses type compatibility to map receiver values to callback parameters and forwards callback returns to call results. The graph projection has a second generic argument/receiver-to-standard-call upgrade. None of these tests establishes the particular native method's effects or callback contract. [`collector-declarations.ts:237–239`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/analysis/program-evidence-collector-declarations.ts#L237-L239), [`collector-call-support.ts:469–547,618–669`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/analysis/program-evidence-collector-call-support.ts#L469-L669), [`anchor-graph.ts:703–717`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/srcly/ops/anchor-graph.ts#L703-L717).

**Implication.** Recognizing `lib.dom.d.ts`, `lib.es*.d.ts`, or `@types/node` answers which declaration supplied a signature; it does not justify “this call stores its arguments” or “this callback's return is the call's value.” JavaScript's permissive inferred types make compatibility-based role selection even less discriminating. React and Solid inherit the same fallback when a specialized row is absent or only partly matches. Correct native behavior requires explicit operation and channel semantics (`SH-02`, `JS-02`, `JS-03`); recognizing a void registration must also suppress an inappropriate generic return fallback.

### SH-F2. Model rows are syntactically validated, not semantically certified

**Source fact.** The JSON/Zod contract supports nine model categories and small fields such as `args`, `returns`, `source`, `accessor`, `option`, and `writes`. The schema checks shape and exactly one exported name/member, but it cannot describe a callback's individual parameter roles, rejected versus fulfilled completion, ignored return, cleanup registration, or a result's `.data` rather than `.status`. Existing library-model tests check parsing, lookup, duplicates, and examples. An empty `ecmascript.json` therefore does not imply no built-in support: important behavior lives in generic collectors. Static JSON inventory here found 0 ECMAScript, 3 web, 35 Node, 6 utility, 14 React, and 32 Solid rows; these are inventory counts, not semantic coverage. [`library-models.ts`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/analysis/library-models.ts), [`library-models.test.ts`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/test/srcly/library-models.test.ts), [model files](https://github.com/byronwall/srcly/tree/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/models).

**Proposal.** Keep the existing declarative loader and add a bounded, typed transfer contract. Separate (1) matched binding/package identity, (2) callback invocation/input roles, (3) call result disposition, (4) state/field effects, (5) applicability conditions, and (6) evidence provenance. Begin with a small discriminated return disposition: void, argument/reference, callback result, returned callable, accessor result, derived scalar, structured result field. Add explicit callback input positions and fulfilled/rejected channels only where a consumer implements them. Reject unsupported row combinations at load time. Do not adopt an unrestricted access-path language before a consumer and counterexample justify each feature. `SH-02` is the mechanism; environment milestones supply the finite rows and fixtures.

### SH-F3. Completed traversal, proof strength, and endpoint meaning are different

**Source facts.** `anchor-graph` yields `partial` for remaining stops, `assumed` for a landed graph with assumed steps, and `ok` for a landed graph without them. Modelled framework/native edges can therefore coexist with `ok`. `facts.ts` recognizes legitimate natural ends such as unused bindings, branch decisions, discarded results, exports, thrown values, and scheduling. Those ends explain where the selected value stops; they are not equivalent to successful rendering or a desired I/O operation. The forward ledger's outcome reducer checks terminal/boundary/budget conditions but does not apply the graph's assumed-proof branch. [`anchor-graph.ts:191–208`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/srcly/ops/anchor-graph.ts#L191-L208), [`facts.ts:208–251`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/srcly/facts.ts#L208-L251), [`value-flow.ts:146–175`](https://github.com/byronwall/srcly/blob/e07cc510087b5c028273cad785b97ee36c6c3b35/engine/src/srcly/ops/value-flow.ts#L146-L175).

The client gives `ok` a green treatment without an explanatory outcome label, uses “proven” vocabulary, and a generic terminal hint describes reaching the DOM even though terminals include other kinds. This can overstate what a user sees. The exact graph-versus-ledger disagreement on a chosen case is an **unexecuted hypothesis**, not a measured mismatch. ## Question 3 — Can offline evidence expose these gaps reliably?

### What TASER actually contributes

Staicu, Torp, Schäfer, Møller, and Pradel's ICSE 2020 paper, *Extracting Taint Specifications for JavaScript Libraries*, describes a **Node.js dynamic taint analysis** with a proxy membrane at library/client boundaries. Access paths describe module members, parameters, returns, and object instances. The implementation combines boundary interception with instrumentation inside analyzed code; it is not merely a logger of arguments and returned values. It needs a taint source/sink policy. Its implementation extracts propagation and additional sink specifications from executed clients, with limited sanitizer handling. The evaluation used 751 selected npm packages and 15,892 clients after exclusions, with 5,707 clients triggering taint activity. The study reports 136 new LGTM alerts; manual review of 30 found 24 genuine source-to-sink flows, which is not a claim that 24 exploitable vulnerabilities were proved. Executed-path dependence, absent coverage guarantees, no implicit-flow analysis, and imperfect static consumers limit generalization. [Paper](https://cs.au.dk/~amoeller/papers/taser/paper.pdf).

The author's project page reports 7,840 propagation specifications and 146 additional sinks across 1,393 modules. These are the authors' historical results, not measurements of srcly or browser frameworks. The [author page](https://cs.au.dk/~amoeller/papers/taser/) and [published repository](https://github.com/cs-au-dk/taser) were checked along with the paper. The supplementary BRICS page was not retrievable through the research browser; the accessible paper/repository sufficed for this comparison. No TASER program was downloaded or run here.

**What transfers to srcly:** explicit boundaries, portable source-to-observation linkage, per-invocation identities, condition/version manifests, and honest incomplete executions. **What does not transfer automatically:** taint as exact value identity; Node instrumentation as DOM support; client test coverage as exhaustive behavior; one observed callback return as the correct API result channel; inferred specifications as proven srcly models. Those distinctions are conclusions of this audit, not claims that TASER promised those capabilities.

### Browser/framework adaptations would be new research

PR #308 proposes observations for Solid memo, batch, and cleanup. An observation of `memo()===token` is useful only for that memo body; a clone-producing memo disproves the broader identity claim. `onCleanup` makes the risk especially concrete: registration returns the callback object, while owner disposal may invoke it later and ignore its result. A packet that records only function registration and eventual payload could mislabel the channel. React adds commit/unmount and stale-capture semantics; vanilla DOM adds native callbacks and host-object identities. These are additional designs, not demonstrated TASER browser capabilities.

Use explicit test-owned adapters before proxying anything. A transparent wrapper can still alter function identity, `this`, arity, getter access, proxy traps, scheduling, stack-sensitive behavior, or framework ownership. Native DOM objects can reject proxied receivers, and spreading or serializing reactive props can execute getters. Do not enumerate arbitrary objects to construct snapshots. Record identity tokens via a WeakMap without traversing values; record scalars only at explicitly selected reads. Compare instrumentation-off and on results, event counts, identities, and exception behavior first. A mismatch invalidates the packet run, not the library model.

An event that never fires, a cleanup outside the observation window, an uncommitted render, a disabled query, or a false resource source supplies **no negative completeness evidence**. Record registration, actions attempted, unexecuted callbacks, pending work, and window closure. A failed equality assertion can falsify a specified universal identity claim; absence of an event cannot by itself falsify possible flow. Conversely, observing a path establishes a witness only for the recorded conditions; it cannot upgrade an entire model to compiler-level proof.

Browser/server entry selection must be explicit. React SSR is not React Server Components. Solid's Node entry can implement different lifecycle behavior from its browser entry. `--conditions=browser` alone is not enough if a resolver still selects an earlier Node condition; record the resolved entry and its bytes. Run each entry as a separate case, with no inference from shared `.d.ts` files. See the version manifest and stop conditions in [experiment-plan.md](experiment-plan.md).

### Comparison with current CodeQL models as data

Current official CodeQL JavaScript documentation describes extensible `sourceModel`, `sinkModel`, `typeModel`, `summaryModel`, `barrierModel`, and `barrierGuardModel` predicates. The API is marked beta. It supports structured access paths and distinguishes `value` from `taint` summaries; its `value` category also includes copying all properties and therefore is **not a JavaScript reference-equality guarantee**. JSON is currently preferred over YAML for model data. This is useful prior art for separating inputs, outputs, fields, callbacks, and provenance, but it is not a drop-in srcly contract or a reason to copy an older `neutralModel` inventory. [Official documentation](https://codeql.github.com/docs/codeql-language-guides/customizing-library-models-for-javascript/).

**Srcly-specific choice:** reuse its JSON loader and Zod contracts; add only the channel/path features required by the selected counterexamples. Store the basis of each claim, finite applicability conditions, and links to positive/negative controls. Keep a hand-reviewed rule distinct from a runtime witness and an unresolved fallback. Adopting CodeQL as a replacement engine would not solve srcly's project admission, UI wording, lifecycle applicability, or generation consistency.

### A justified alternative: generated semantic mutations and approximate interpretation

For near-term correctness, generate small counterexamples from the same fixture: retain/discard a return; inline/name a callback; canonical/renamed import; direct/lifted dispatch; one/two instances; included/excluded prop; resolved/rejected Promise; called/never-called handler. Mutate the proposed model deliberately—make all effects return their callbacks, swap a callback index, erase a field filter—and require the suite to catch the wrong rule. This is an **original testing proposal**, not a claim of measured mutation-detection rates. It targets the exact kind of broad but green rule found here, cheaply and without runtime capture.

For a later research branch, Laursen, Xu, and Møller's PLDI 2024 approximate-interpretation work uses dynamic hints to improve static analysis of JavaScript. The associated Jelly project offers flow-insensitive call/points-to analysis and explicit soundness limits for Node-oriented JavaScript/TypeScript. This is relevant to computed property names and dynamic call targets, not a ready-made framework lifecycle oracle. Explore a tiny authored initialization/key-resolution case after direct correctness work; do not replace the engine or promise browser/React/Solid coverage from Node results. [Author project/paper](https://cs.au.dk/~amoeller/papers/approx/), [Jelly repository](https://github.com/cs-au-dk/jelly).

### Technique scores and decision

Scores are **ordinal engineering judgments, not experimental measurements**: 0 weak/no direct evidence, 1 limited, 2 useful with controls, 3 strong for the finite property. The vector is **wrong flows / missed flows / identity–derivation / callback–lifecycle / usefulness with incomplete execution**. Maintenance effort is relative to srcly's current harness. These scores compare methods on this mission, not universal research quality.

| Technique | Scores and maintenance effort | Role in the recommended approach |
| --- | --- | --- |
| Ordinary semantic assertions plus annotated static fixtures | **3 / 2 / 3 / 2 / 3**; low–medium | Primary oracle. Negative endpoints, channel/field assertions, and direct runtime equality/order establish finite contradictions. Must include real JS and fixture setup, not only TS end kinds. |
| Hand-written library rows alone | **1 / 2 / 1 / 1 / 2**; low initially, medium over versions | Necessary implementation medium, weak independent validation. Rows become useful evidence only with exact source contracts and counterexamples. |
| Boundary observation packets inspired by TASER | **2 / 2 / 2 / 2 / 1**; medium–high | Optional review aid for invocation/owner/window provenance. Stronger only if enriched with direct assertions; unobserved behavior remains unknown. Generic proxies add perturbation risk. |
| Differential/metamorphic checks against pinned real libraries | **3 / 2 / 3 / 3 / 2**; medium | Primary companion to fixtures. Compare semantically equivalent forms and discriminating variants, including direct versus lifted dispatch and browser versus server entries. |
| Generated counterexamples plus deliberate model mutations | **3 / 2 / 2 / 2 / 3**; medium | Best next test investment. Shows whether the oracle rejects a specific wrong model, even when no callback executes. Mutation catalogue remains bounded and reviewed. |
| Approximate-interpretation/dynamic-key hints | **1 / 3 / 1 / 1 / 2**; high | `EX-02` research only. Potentially reduces dynamic-key/call-target misses; does not certify identity, timing, or model truth. |

**Hybrid decision.** Build `SH-01` exact fixtures and semantic mutations, `SH-02` typed models, and paired real-library assertions. Explore packets on the same sixteen cases without changing their inputs or claims. Keep a packet format only if it identifies a valid missing channel/identity/condition or changes a justified model review that ordinary assertions did not. If it merely repeats values and counts already asserted, omit it from required CI; a compact assertion report is enough. Do not make the three environment tracks wait for this research decision. `EX-01` is bounded and can be rejected without losing any build milestone.
