# Data-flow coverage: what landed

This file records the data-flow coverage work that is in `main`. Open work is in the backlog grid (`pgm/data`, see `AGENTS.md` → Backlog), not here.

The work came from the data-flow experience audit (October 2026). The audit traced about 120 exports per repo on six repos and ranked where traces stop. Each PR below removes one cause of a false stop, or names a stop that was silent.

## How coverage is measured

- `engine/scripts/survey-blockers.ts` traces a sample of exports in both directions and writes every outcome and stop as JSON (#162). `engine/scripts/survey-report.ts` ranks the stops.
- `pnpm survey-gate` (CI's `survey` job) surveys `client/`, `server/` and `examples/value-flow-basics` and fails on any move the PR does not record (#192, #205).
- A rule's test is an annotated fixture in `engine/examples/value-flow-basics/src/`. `engine/test/srcly/fixture-annotations.test.ts` checks the `@trace`, `@outcome`, `@reaches` and `@stop` claims (#201). `@path` and `@no-path` name a route between two labelled boxes, so a wrong route to a legal end fails. `engine/examples/value-flow-js/` runs the same claims on actual `.js` files, after a check that each file is in the Program.
- The r3 survey, before #198, was 19% ok: TypeScript 16%, Python 25%.

## Outcomes and honesty

- A trace says what each side holds and where it stops (#151, #152, #155). A frontier box is labelled by why the trace stops (#158), and every partial trace names its stop (#169).
- `ok` means proven. A trace that lands only through an assumed library step is not `ok` (#183).
- Per-call contexts: each factory call and each `new` is its own context. A closure a factory returns reads only what that call captured: `makeReader(a).read()` reaches `ra.read()` and never `rb.read()`, and a `let` one returned function writes and another reads (`makeCell`: `ca.set(x)` reaches `ca.get()`, never `cb.get()`) stays in the call that made both. A class's instance field written through `this` (in the constructor or a method) or a named receiver is read only through the same instance: `new Box(c).get()` never reads `new Box(d)`'s value. Both directions. A closure called in its factory's own body (a local helper such as `owner` in `foldGraph`) runs in the frame that called the factory and adds no instance; before, the backward walk dropped such paths without a stop. The collector tags each call with the instance it runs its target in (the call or `new` its receiver came from: `const la = makeLabel(…)`, `const { get } = makeCell(…)`, an imported `const`, or `this`) and each instance member's write and read with their receivers' instances (`InstanceTag` in `engine/src/analysis/scope-seam.ts`, `madeBy` in `engine/src/analysis/instance-sites.ts`); the slice keeps a walk in one instance (`evidence-slice.ts`: the invocation stack holds the instance a member read was made in). Where no name says which instance it is (an element of an array, a field, a `let`, an untyped value), the trace still reaches every reader, and when the factory or class has more than one call or `new` site that step is assumed (`shared-instance`), so the trace reads `assumed`, not `ok`. Fixtures `instance-state.ts`, `object-calls.tsx` (`Slots`). Survey gate: value-flow-basics `ok` 124 → 130, `assumed` 8 → 7; client `ValueFlowLedger` `ok` → `assumed`, because its upward walk now crosses `foldGraph`'s local `owner` closure and reaches `rename(…)`, a callback parameter with no body. Before (#427), any factory or class with more than one site made these traces `assumed`.
- An in-project wrapper binds a call of its result to the function it is given only when the call's type is that function's type (`wrap<T>(fn: T): T`). `compute(fn): () => number` makes another function, so `total(x)` after `const total = compute(…)` never reaches the callback (fixture `wrapper-returns.ts`). A selector hook that returns a member function (`useStore((s) => s.relabel)`) no longer binds to the selector.
- `Object.assign({}, a, b)` keeps each source's fields under their own names, as a spread does (a `passes-through` row on `ObjectConstructor.assign`; fixture `assign-fields.ts`).
- Every relation between two boxes is kept as its own edge (its kind, field and proof), and the view draws them as one edge that lists them all at the strongest status. A field edge is named by the field it moves, whichever way the walk came. A pair of boxes is assumed only when every edge joining them is. The ledger takes the same `assumed` rule (`assumedCallee`), so `slugify(props.title)` reads `assumed` in both views. Before, the first relation the walk met named the edge and the rest were lost: on srcly's own client, 3,509 dropped relations differed from the one kept (2,051 lost a field name, 1,069 a second relation kind such as `consumer-value`).
- The ledger and the graph give the same answer for one expression (2026-11-23). The ledger is the anchor graph for the same selection, laid out as rows: its steps (each with the edge's relation, status and proof), then every end and stop it names, and its outcome. It has no walk of its own, and over the byte bound it fails with the graph's own `budget-exhausted`. A value that ends where it is selected (`unusedHeight`, never read) lands at the input row. A call the selection is made of says how the value was made, never where it stops: a call into code with no source, or a first-party call with many unpaired call sites, is a partial transform row that names why (`external-code`, `unproven-handoff`), not a stop. The ledger is bounded: it lists the paths that reach an end or a stop (one step per box, at most 64 step rows, and the input row says how many it left out), then every end and stop. `engine/test/srcly/ledger-graph-agree.test.ts` checks every forward text anchor in value-flow-basics, value-flow-js and value-flow-loose: the same outcome, each stop's reason at the same line, the same ends, and no step the graph did not draw. A probe over every selectable expression agreed on all 11,716 in value-flow-basics and all 866 in python-anchors. Before, the ledger copied the graph's stop rules, and the copies drifted: 13 of 243 fixture anchors differed, and a wider probe found 145 of 6,032 TypeScript and 44 of 704 Python selections (row caps, aliases, crossed boundaries, escaped callbacks). The ledger for `item.node` in `HotSpotList.tsx` now reads `partial`, as the graph always did: the value goes on into `HotSpotItem` and stops at `ctx.onSelect(…)`.
- A canvas of several anchors keeps each trace's witnesses. An edge two traces draw keeps every relation and proof, and names the traces that have it; reach emphasis walks one of the seed's traces at a time, on that trace's own witness for each edge, so `id(props.a)` never lights `id(props.b)`'s slot through the shared helper (PW01), and another trace's proof never carries a path past a stop. A merged edge's id is its box pair. A reference folds only over a proven `references` link, and the edge it leaves keeps that link's proof (PW05). `client/src/viz/deps/flow/projection.test.ts` checks PW01, PW03 and PW05 on the engine's real graphs (`engine/test/srcly/projection-fixtures.test.ts` writes them).
- A return of a function that no call names, only handed on as a value (a callback, a nested `def` passed to a runner), is an unproven hand-off, not where the value leaves: the trace is `partial` and names it. The Python helper counts a nested function read as a value as escaping.
- A function anchored by name walks its body forward: each parameter reaches the function's writes, calls and returns, so a handler shows what it does with its input and reads `partial` when its body stops inside. Before, it walked only returns and uses, and `create_item` read `ok` with its database write off screen.
- Backward from a field read, the anchor graph names the field's producer (`producers`, #442): the expression packed as that field where the slice's own field path ends (`engine/src/srcly/field-producers.ts`, reusing `stepFieldPath`). A step that widens the path to the whole value ends it, so a whole object carried somewhere is never a field's producer. A state pair's seed is a `state-initialization` proof, kept apart from a later write (`framework-state`); both stay `partial`, because the read may see either. The trace question shows the read, one proven producer, the handoff (initialization, return or field) and later writes; two first values, a shared component's callers and a call nothing returns into stay named, not answered. Fixture `examples/value-flow-basics/src/field-producers.tsx` (`@produces`).
- A budget-exhausted route slice names its omission (#161). Size limits are spent only on fields the trace reads and places it draws (#168, #197).
- When nothing is drawn, the view says why and offers to try again (#160).
- A trace over 40 boxes opens folded: the anchor's own function in full, each other function as one box with its file, step count and ends ("reaches database write, response"). A box opens in place. `User.email` forward went from 62 boxes to 11, `SECRET_KEY` both ways from 177 to 33.

## TypeScript rules

- Dead ends: four kinds carried past (#167); four more found by fixture annotations (#202). Backward, a parameter of a function handed to a package (`handleSubmit((values) => …)`) begins in that package, as an external import does. Backward, an empty `{}` or `[]` is where a value begins, as a literal is.
- Reads and writes: a read sees every assignment that can reach it (#173); a compound assignment to a field (`ref.current += step`) writes its right side into the field, as `=` does; a computed key is a partial read of its receiver (#171); a computed key in an object literal (`{ [row.k]: v }`) picks a field and ends there, as `obj[k]` does; array elements, spreads and `for…of` (#174).
- Calls: the slice's call pairing is trusted at every helper (#170); a function's field reads land through its argument (#163); a first-party method is entered through `this` (#176); `new X(…)` and `super(…)` enter the constructor the checker resolves, a parameter property (`constructor(public label)`) writes its member, and a getter's returns are what a read of its member sees; a generator's `yield x` reaches the loop over its call; a call is paired with the one function its value is, through objects, bindings and aliases (#198, `engine/src/analysis/value-origin.ts`). A call through a function-typed parameter or prop (`visit(item)`, `props.onSave(v)`) enters each function a caller hands in, paired with the call or occurrence that handed it in, so two callers' handlers never cross (`bound-handler`). A setter handed in (`onPick={setPicked}`) writes its state, a context method (`store.save(x)` after `useContext`, or a destructured `{ save }`) runs the provider's function, and so does a context whose value is itself the function (`const dispatch = useContext(Dispatch)`), a backward trace out of a handler leaves only through the caller that handed it in, and an arrow whose body is a void call returns nothing to its call.
- Library calls: a discarded call's arguments stay in a receiver its function declares (#175), and in a closure's variable, a parameter, or an element of one (`groups[key].push(row)`); in module state only when the module's own unexported container is read back in its file (`cache.set(k, v)` reaches `cache.get(k)`), never a write-only log or state shared across files; the write lands in the field the receiver names (`section.rows.push(row)` reaches `section.rows`, not `section.title`), and a push written as a void callback's body (`forEach((x) => rows.push(x))`) is a write; a library call's receiver reaches the function it is given (#184); a call made for its effect through a function a library hands back under a local name (`navigate(url)` after `useNavigate()`, `setSearch(…)`, `refetch()`) is an assumed external effect, resolved through the checker's signature, never a dead end; calling a function held in a field (`props.onPick(x)`) does not write `x` into the object; a library call is known by its import's module and export name (#209). A read through a namespace import (`api.greeting` after `import * as api`) reads the export itself. A wrapper call (`action(fn)`, `useCallback(fn)`) returns the function, so what the function returns reaches the wrapper's call sites, never the wrapper call itself.
- Call results: a React effect's call has no value, so what its callback returns (a cleanup) is not the hook's result, and generic callback handling cannot restore it (`returns: "void"`). `mutation.mutate(x)` and `mutateAsync(x)` enter their `mutationFn` as a call enters a function of the project's, so two calls on one hook stay apart and a payload the function drops reaches no result. Only `mutateAsync` hands the return back.
- Query results: a query's result is an object of fields, and only `data` holds the fetched value: what `queryFn` returns, or what `select` returns when the options have one. `select` takes what `queryFn` returns, so a field it does not read stops at its parameter. `status`, `error`, `isLoading` and the other fields never hold it. A mutation's `data` is what its `mutationFn` returns; `mutate` still has no value. A row's `field` and `selector` say this (`engine/models/react.json`). A destructured result reads its own field: `const { data, isPending } = useQuery(…)` carries the value into `data` only, and `rows?.length` after `const { data: rows }` walks back to the fetch. `useInfiniteQuery` keeps the whole-value rule.
- Query cache: `QueryClient` methods are `member` rows of `@tanstack/query-core`, found through the class the checker resolves. `getQueryData` is an external read, `setQueryData` and `invalidateQueries` (and their siblings) change the cache, an external effect; `useQueryClient()` is the provider's client, an external read. Like a service read, a cache read's key and client stay inputs to its value. A dropped call a row names (`client.setQueryData(k, v);`) no longer keeps its arguments in its receiver. A method no row names is unchanged (`query-cache.tsx`). The cache is a keyed store (`keyed` rows, `engine/src/analysis/keyed-stores.ts`): what `setQueryData` writes (or an updater returns) reaches a `getQueryData` of the same key on a client from the same source (`useQueryClient()`, one `new QueryClient()`). A constant key (a literal, a `const`, an array of them) joins as modelled; a computed key (`["user", props.id]`) may be any key, so its join is assumed (`computed-key`). Another key never joins. `localStorage` and `sessionStorage` are keyed stores of their own in the same way (`Storage.*` rows in `engine/models/web.json`): `setItem` reaches a `getItem` of the same name on the same storage (`keyed-stores.tsx`).
- Solid resources: `createResource(fetcher, options?)` has no source and `createResource(source, fetcher, options?)` has one, read per call from its `cell` row's `optional` source (`asyncCellFlow`). The fetcher's return, inline or named, is the resource's value, and `initialValue` reaches it too. The source fills the fetcher's parameter and never reaches the resource by itself, so a source the fetcher ignores stops at the source. A `.json()` call the fetcher only reads does not reach the resource: the exact carrier needs the fetcher to return that value, through an `await` or a const binding, and a reshaped body goes by its fields. `mutate(v)`, destructured from the resource's second element, sets the value its reads see, as a setter does; `refetch(x)` runs the fetcher again with `x` as its second parameter's `refetching` (the row's `writes` and `yields` paths). Neither call is an assumed external effect any more, and neither call's value carries its argument.
- Solid results: `createEffect`, `createRenderEffect`, `createComputed` and `onMount` have no value. `onCleanup` returns the function it is given. `on` returns a new function, and its callback's return reaches a call of that function, never the `on` call. A selector's call is a boolean test of its source. `batch` and `untrack` still yield what their callback returns. Renamed imports (`createSignal as signal`) match the same rows. `const x = call(fn)` no longer makes `x()` a call of `fn` when a row says the call makes something else.
- Solid render callbacks: `<For each>` hands its callback (inline or named) each item as a value, and `<Index each>` hands it each item as an accessor, so `row.name` and `name()` both read the item. The second parameter (`For`'s index accessor, `Index`'s index number) is not fed from the list, and `each` is not a DOM attribute. `<Show when>` and `<Match when>` hand their value as an accessor, or as the value itself when `keyed`; a `keyed` set to a value no reader can decide hands neither, and an accessor parameter's own fields (`doc.length`, its arity) stop the trace. `ErrorBoundary`'s function `fallback` takes the error, which no prop supplies, and is not a DOM attribute. These components are `slot` rows (`engine/models/solid.json`, read by `engine/src/analysis/slots.ts`), with `Switch`, `Suspense` and `solid-js/web`'s `Dynamic`. Fixtures `engine/examples/value-flow-basics/src/{solid-render-callbacks,solid-show-keyed}.tsx`. A library callback whose item the library declares as a function of no arguments (`indexArray`'s `Accessor<T>`, read from its declaration, not its name) reads the item at each call of that parameter. Solid's bound handler `onClick={[remove, id]}`, known by the attribute's tuple type, binds `id` to `remove`'s first parameter, and the pair ends there, handed to the page.
- Loose projects: a jsconfig or tsconfig with `strictNullChecks` off is analyzed, and so is a folder of JavaScript or TypeScript with no config, whose options the engine infers in memory (it writes nothing to the project). Every result says `nullProof: false`, and an empty `tsconfig` when there is no config, and the rail reads "No null proof". A trace holds the same way, but no rule may read `undefined` from a type there: `mergeProps` only trusts a later literal. A broken config is still refused by name. The `tsx-dataflow` report still needs a real config, because its nullish verdicts read those types.
- Promises: a promise's outcomes are separate channels, read from `settles` rows in `engine/models/ecmascript.json`. A fulfilled value reaches the first callback of `then` and never a rejection handler. `then` holds what its callbacks return, not its receiver. `catch` keeps the fulfilled value and adds what its callback returns (recovery). `finally` keeps the fulfilled value, its callback takes nothing, and what the callback returns ends there. A named handler (`.then(show)`) is entered as a written one is. `Promise.reject(reason)` holds no value: the reason reaches a `catch` or a second `then` callback, over any `then` or `finally` between them, and with no handler in sight it ends there as a thrown value does. `reject(reason)` in `new Promise` ends there too, and only `resolve` hands a value back. A rejection from a `throw` or from a promise the code does not show is not traced, so the handler's parameter starts there.
- Native writes: whether a standard method changes its receiver comes from its row in `engine/models/ecmascript.json`, not from the caller dropping its value. `const n = rows.push(row)` keeps `row` in `rows`, and a dropped `rows.concat(row)` keeps nothing and ends there. A method of the project's own with the same name keeps its own meaning.
- Native callbacks: an `Array` method's row in `engine/models/ecmascript.json` names what each callback parameter takes (`parameters`). `map`'s `index` takes a position, never an element; `reduce`'s accumulator takes the seed and then the callback's own last return. The callback's return reaches the call's value only for `map`, `flatMap` and `reduce` (`returns: "callback"`): `forEach` drops it, and `filter`, `find`, `some`, `every` and `sort` only test or order with it. A callback of one element whose return the call does not yield (`filter`, `find`, `some`, `every`) tests that element, so its return ends as a `branch-condition`; a comparator (`sort`, two elements) still ends at its return.
- Receivers and keys: `bag["x"] = v` packs `v` under `x`, as `bag.x = v` does, and a read of `bag["y"]` takes only field `y`. A computed key (`bag[key] = v`) packs into some field, a `partial` step every read of `bag` may see. Assigning a setter the project declares (`cell.current = v`) runs it: `v` binds its parameter and `cell` its `this`. A member's state is still the class's, not one instance's.
- Call adapters: `f.call(t, a, b)`, `f.apply(t, [a, b])` (a list written out) and a call of what `f.bind(t, a)` returned run `f`, with `t` as its `this` and the arguments shifted into place, so an argument `f` drops reaches nothing. A value bound ahead (`this` or a leading argument of `bind`) enters `f`, but its return is not paired back to the later call: it stops at `unproven-handoff`.
- Contexts (`keyed` rows on `createContext` and `useContext`, `store: "providers"`): `useContext(Ctx)` gets the value of the nearest `Ctx` provider above the reader, or the `createContext` default where no provider is above it (`engine/src/analysis/program-evidence-context-ancestry.ts`). The walk goes out from the reader to its component or hook, and out from each place that one is rendered or called. A provider whose subtree has no reader supplies nothing. React 19's `<Ctx value>` is a provider too, never a DOM attribute or a component. The context object is not the value read. Where a mount is not known (an exported component nothing renders, a component handed on as a value, a render prop, a component that renders its own provider around children), every provider outside the components walked through, and the default, are candidates. A hook's one `useContext` call serves every caller, so each caller gets every value any caller may get. A context method resolves through a hook of the program's whose one return is the `useContext` call (`const cart = useCart()`, then `cart.add(x)`), and a context's value keeps its field path to the reader, so `cart.items` never sees what `add` takes. A state pair provided whole (`value={pair}` after `const pair = createSignal()`) gives a reader's element 1 as its setter and element 0 as its getter. Forward through a framework's state (a setter's write, then a getter's read) the walk is in no one call, as through a member's state, so it can leave the hook that read the context. Backward keeps the call stack, as before.
- Local callback props: a forward trace through a component’s prop call loads checker-matched JSX occurrences with that named prop on demand. It reuses the same occurrence-bound proof as the eager collector. An unresolved supplied callback does not gain any state or render edges.
- Reducers: a dispatch reached through a prop or a context runs the reducer as a direct one does. It used to write its argument straight into the state, so a reducer that ignores its action still showed the action in the render. A function given to a dispatch is an action: nothing calls it.
- DOM reads: a dropped `querySelector`, `closest` or `getAttribute` call is a read, not a page write. `engine/models/web.json` names the finite list. A DOM method it does not name keeps the old rule, and a project's own `querySelector` was never the page.
- Result cache: the engine fingerprint covers the library model rows, so a changed row misses the cache in a checkout and in a bundle.
- Components: prop reads in closures and string-literal props bind to the caller (#159); destructured and optional props bind (#186); a prop binds to a field read of a view of the props (a `const` copy, or what a `passes-through` row returns: `mergeProps(defaults, props)`, both halves of `splitProps`), when the view holds that field: each half of `splitProps` holds its own keys, `mergeProps` takes a field from the last source that sets it, and a key list the code computes or a later value that may be undefined keeps the prop; `mergeProps` keeps a field through the call, so a default for `kind` never reaches `merged.other`; a factory or alias component renders at the JSX tag that names it (#180); a default-exported function anchors by its own name (#178).
- Handed-on props: a JSX spread of a props view (`{...rest}` after `splitProps`, a destructured `...rest`, `props` itself) hands on each field the view holds, unless a later attribute of the same tag sets it. The prop goes into the child's own read of it, through a binding at the spread, or into an element's attributes (`<input {...rest} />`). A child the program cannot see, or one that never reads the prop, stops it at the child's tag, as before. A callback prop handed on (`onRemove={props.onRemove}`) runs what the outer caller hands in, up to four levels (`component-forwarding.tsx`).
- Rendered components: a tag renders what the checker proves its value is. That is the default export of the module a loader imports (`lazy(() => import("./chart"))`, which names its loader, not the component), the one function an in-project factory returns (`withLoud(Heading)`), and, for a component parameter of an in-project function, what every call of that function passes (the function must be used only by calls). It is also each component a literal key type picks from an object (`<Dynamic component={kinds[props.kind]}>`): an occurrence that renders several components binds each, and names no one definition.
- React class state: what a class component's static `getDerivedStateFromError` or `getDerivedStateFromProps` returns is what its declared `state` member holds, when the class extends React's `Component` or `PureComponent` (`react-derived-state.tsx`). `this.setState` is not modelled yet.
- State: every library state is a `cell` row (`createSignal`, `useState`, `useReducer`, `createStore`, zustand's `create`, `createResource`, `useSubmission`): its `init`, `writes`, `reads` and `yields` access paths say where each call's one state is seeded, written and read (`engine/src/analysis/cells.ts`). A cell made inside a function is one state per call of it: two `makeCounter()` calls never share a signal, and a step the walk cannot pin to one call is assumed when the function has more than one call site. A zustand store holds what its function returns and what its `set` receives; a selector reads the field it names, and calling a member read through the hook (`setCount` after `useStore((s) => s.setCount)`) runs the store's function, never the selector it is written beside. Middleware passes the store's function through when the checker types its parameter and its result as the type `create` declares for its function (`persist(fn)`, `immer(fn)`, `devtools(fn)`); no middleware or type is named. A slice creator the store's function calls with its own `(set, get, api)` (`fishSlice(...a)`) adds its return and its own `set` writes to the same store, and its members run when the store is read whole (`const { addFish } = usePond()`). An updater's parameter is the store's draft (the row's `….Parameter[0].Parameter[0]` write), so `draft.notes.push(note)` writes the store. A slice two stores call writes each of them, assumed (`shared-instance`), since the walk cannot tell which store's call ran it. A creator's `get()` and a `subscribe` listener's parameter read the store. `useStore.getState()` reads the store, and its members run (`usePond.getState().rename(next)`); `useStore.setState(x)` is the store's `set`. A store write is modelled like a state setter: never an assumed external effect, and its call holds nothing. A destructured read takes the fields it names: `const { fishes, addFish } = usePond()` sees what is written to `fishes`, not to `owner`. a setter's value reaches its getter's reads (#182); a function handed to a setter (`setCount((c) => c + step)`, a store path's `setState("todos", (list) => […])`) stands for what it returns, and its parameter is the current state; a Solid store path (`setStore("left", "title", v)`) writes `left.title` alone, so a sibling field never sees it, an updater there (inline or named) receives that field, not the whole store, and a predicate in the path (`(item) => item.id === id`) is a test, never stored; a store or signal's initial value seeds it field by field, so `createStore({ left, right })` keeps `left` and `right` apart; a cell whose `init` names `Argument[0].ReturnValue` (React's `useState`) calls a function initial value, and Solid's `createSignal` holds it; a `useReducer` dispatch binds the reducer's action, and the reducer's return is the state; cell factory and getter calls are framework-modelled (#188), modelled in the collector (#196).
- Ends: a binding every read of which decides a branch (`if (forgotten)` in nested branches, `ready && <X />`, `<Show when={isVisible()}>`, through `!` or an accessor's call) ends at its binding, decides a branch. A parameter or local binding the program never reads (`_level`, `const { isSuccess } = useQuery()`) ends there, named "never read": the checker proves the value goes nowhere, so the trace is `ok`, not a dead end; the value-flow ledger draws every in-place end (a branch test, a write, never read) as a terminal row, as the graph does. A service write or read is a method on a client's contract, or a function-valued field a declaration file declares (a generated client's); a callback prop the project declares (`props.save(x)`) is never one. A thrown value ends at the throw (#207). An exported value that nothing in the program reads ends at its export, the module's API, not at a dead end; a call through a callback an export nothing in the program calls was handed (`onSeen(id)`, `props.onPick(x)` in a component nothing renders) ends there too, at the module's API, never a library method on a parameter (`items.forEach`); one the program reads, by name or through `import * as`, walks on to that read. A function handed to a timer (`setTimeout`, `requestAnimationFrame`) ends there: the callback runs later. A function handed to a page element as a handler (`<button onClick={click}>`) is not an escape: the page drops what it returns. A trace whose anchor has nothing beyond it names a stop at the anchor. A context `Provider`'s `value` goes to its readers, never into the page. A request ends a forward trace where it is sent, and a backward trace lands at the request a response came from: neither stops at the response body. A promise chain the code drops (`load().then(show);`) ends there. A function library code hands to a callback (`resolve` in `new Promise((resolve) => …)`) hands its argument back to the call that supplied it: the value reaches that call's value, and the call through it ends there, handed back. A DOM call the code makes for its effect (`el.classList.add(x);`, `target.dispatchEvent(e);`, `() => input?.focus()`) is a page write: any member TypeScript's DOM lib declares, whose value the code drops. A DOM call whose value the code uses (`root.querySelector(sel)`) carries on. An arrow whose body is an optional void call returns nothing. `response.json()` on a `fetch` result reads the body; only a server's response is an HTTP response. An emitter's `emit("name", x)` binds each listener its receiver registered with `on("name", fn)`, and `yield* list` hands on `list`'s elements. A return that is a call (`yield items.slice(…)`, an arrow's `() => f(x)`) is judged by its own function's call sites, never the call's, so an exported generator no code iterates ends at its return. A class's annotated uses fold by file (#208). A `when` on Solid's `Show` or `Match` ends as "decides a branch", not a DOM attribute.

- Solid catalog: 90 patterns (58 new: stores, router data, components, reactive helpers, lazy). All 90 are `ok` and reach the wanted end (79 before the rules below, 74 before handed-on props and rendered components). `s-index` wants `render-terminal` (a text child) and `s-filter-memo` wants `branch-condition`: the query only picks which items render, so it is never a rendered value.
- Submissions: a `calls-back` row with a `field` and no `option` watches the function it is given (`useSubmission(action)`, `watchedFunction`). Its result's `field` (`result`) holds what the action's function returns, and its `input` field holds each call's arguments by position, so `submission.input?.[0]` reaches the literal a call of the action passes and never another action's.
- Stores: `setStore(produce(fn))` hands `fn` a draft of the store, and what it writes into the draft (`d.body = v`) is that field of the store. A getter that reads `this` (a store seed's `get full()`) takes `this` from the receiver of each read of its member, so `this.first` reads the store's `first`.
- Calls: a getter returned through a call whose value is its callback's return (`createRoot(() => { …; return n; })`) still reads its state. A function written as a component element's one child is its `children` prop, so `props.children(x)` binds it; it is handed in at the element's opening tag. A function written as a prop of a package's component (`<ErrorBoundary fallback={(err) => …}>`) is filled by that package: its parameter begins there.
- Fixture `engine/examples/value-flow-basics/src/solid-actions-resources.tsx`. The fixture project has no Solid types, so the two rules that read them (`indexArray`'s accessor item, the bound handler) are checked by the catalog's real `solid-js`.
- A call that has a flow row is modelled, never an assumed effect. New rows: `createDeferred`, `createRoot`, `mapArray`, `makePersisted`. A state pair passed through a one-argument passes-through row stays a state pair.
- A terminal row can name the function a hook hands back (`result`: the call, or a tuple index). A call of what `useNavigate` returns, or of the setter from `useSearchParams`, is a proven end.
- `props.count()` reads the accessor's value when each occurrence of the component binds an accessor to that prop.

- React catalog: 81 patterns (46 new), 70 `ok`, 5 assumed, 6 partial, 73 at the wanted end (60 before handed-on props, rendered components and class derived state; 63 before zustand middleware, slices and the store API; 68 before destructured fields and the query cache). `q-closure` anchors at the `queryFn` closure's own read: its first anchor was the key's copy of `props.id`, which honestly ends at the options object. The actual-JavaScript root has 21 patterns (18 new), 17 `ok`.

- Module `let`: an assignment to a module-level `let` in one function reaches its reads in another (`select(name)` writes `current`, `selected()` returns it). The read sees each binding that can reach it, as it always did; the demand collector now loads the functions that read the variable when a trace goes forward from an assignment, so the trace no longer stops at `current = name`. A module `let` nothing reads back still stops there. Fixture `module-let.ts`.
- Constructor functions: `new Account(owner)` runs a JavaScript constructor function as it runs a class's constructor. `new` yields the object, never what the function returns. A method assigned once (`Account.prototype.describe = function …`, an expando `f.x = …`) is what a call of that member runs: the checker declares such a property by its assignment, so one declaration is one value (`resolveValue`). A value written into a member (`this.owner = owner`) loads the member's reads in other statements. Fixture `value-flow-js/src/constructor-functions.js`.
- JSON values: a value parsed from JSON (`JSON.parse(text)`, a fetch `Response`'s `json()`, through `await` and `const` copies) is typed `any`, but it is only ever null, a boolean, a number, a string, an array or a plain object, with no function of its own. A method only one of those prototypes declares (`map`, `reduce` are `Array`'s; `toLowerCase` is `String`'s) is that standard method, with its row (`jsonValueMember` in `engine/src/analysis/value-origin.ts`). A name several declare (`slice`) stays a stop. Fixture `json-values.ts`.
- An untyped receiver of unknown origin (a JavaScript parameter: `items.reduce(…)`) stays an `unresolved-symbol` stop, now named: "the receiver is untyped (any) and its origin is not known". Any object may stand there, so a method's name does not say which function runs. Fixture `value-flow-js/src/untyped-receivers.js`.
- Catalog after these rules: actual JavaScript 19 `ok` of 21 (17 before), vanilla 37 of 38 (36 before).
- A hook's result holds only what its row names. A `useMemo` dependency list and a `useQuery` options object end in place as a hook input. Before, a dependency and a `queryKey` reached the result as `ok`.
- Row fields `hands`, `observers` and `contextFrom` join option callbacks: `queryKey` reaches `queryFn`, `getNextPageParam` reaches `pageParam`, and a mutation's variables, result and `onMutate` context reach `onSuccess`, `onError` and `onSettled`. An observer with a destructured parameter gets no binding yet.

## Symbol view of an anchor trace

The symbol view is the default drawing of an anchor trace. `?model=steps` (the Steps toggle in `FlowTools.tsx`) keeps the old one-box-per-step view.

- One box per symbol. Boxes merge by scope and checker symbol id, which the anchor-graph contract carries as `symbol` and `field`, never by label. A node with no symbol keeps its own box. A merged edge keeps every original proof. On visual-notes' DocView this cut 557 boxes to 225.
- The anchor-graph contract is the one seam: `engine/src/srcly/contracts/anchor-graph.ts` feeds `client/src/viz/deps/flow/anchorAdapter.ts`. Each fact the view needs (symbol, operation, `symbolKind`, frame `role`, links) is an additive field on it.
- Value flow is the bold main line, with its operation named on the edge. Calls, reads and writes are thin links that can be toggled.
- `symbolKind` (state, transform, origin, end, plain) carries the strong color. Frames stay neutral and name their role: component, hook, helper, handler, fetcher, server or unknown. Roles live in `engine/src/srcly/scope-roles.ts`, never in `engine/src/analysis`. Unknown is never drawn as a component.
- The first screen is the main path from origins to ends. Side branches are stubs that grow with `+` and `−` or the depth control (1, 2, 3, all) in `depth.ts`. Depth is in the URL and the view-state registry.
- Plain TypeScript modules with no routes or components are an equal target.
- Tune the view on `engine/examples/symbol-graph/`. Use a large app such as visual-notes to check scale and find engine errors.

## From the terminal

- `srcly trace <path>[:line[:col]] [--symbol NAME]` prints an anchor's origins, ends, paths and stops as compact markdown, or the full contract with `--format json`. It works on TypeScript, TSX, JavaScript and Python. `--effects` prints a function's reads, writes and calls (TypeScript only: the engine's effects view has no Python side).
- `srcly impact <path> --symbol NAME` answers the refactoring question: each parameter's ends, the return's ends in each caller, and the call sites. It lists a place as proven only when the trace is proven. A partial trace goes under "Not proven" with its stop.
- The logic is in `server/app/services/dataflow/trace.py`. The engine is unchanged.

## Python type source

A Python root uses the same engine contracts as TypeScript. `engine/python/srcly_pyfacts.py` provides the evidence. The engine runs it once per generation.

- Structure comes from the standard library's `ast`. Types and call targets come from mypy's `build.build` with `export_types`. The helper prints ProgramElement and ProgramRelation facts in the collector's raw shape.
- A box's type is mypy's type at that span (`typeSource: "mypy"`). Where mypy has none, such as a parameter or a file it could not check, the annotation text stands in (`typeSource: "annotation"`). A pydantic or dataclass field read cites the field's declaration as proof.
- mypy names the function or method a call reaches (`CallableType.definition`). This gives argument-to-parameter and return-to-call relations without guessing.
- mypy reads the project's own packages through `python_executable`: the project's `.venv`, else `VIRTUAL_ENV`, else the helper's interpreter. mypy is a dependency of srcly's server. When mypy is missing, the engine refuses with `python-checker-not-found`.
- Rejected: annotations over `ast` alone (would need a hand-written inference engine for unannotated code), `pyright --outputjson` (diagnostics only, no types) and pyright's language server (one hover at a time, about 65 s for `server/app`, display strings with no call structure).
- Measured on 2026-10-24 on srcly's `server/` (59 files): 4.9 s wall, of which mypy took 2.3 s, and 563 MB peak RSS. mypy typed 91% of expressions precisely.
- Origin and terminal roles come from each element's `kind`, so new Python recognition goes in the helper's tables and in the `py` rows of `engine/models/python.json`, never in `engine/src/analysis`.
- A file with syntax newer than the helper's interpreter is rewritten when an older spelling keeps every column: `except A, B:` (PEP 758) becomes `except(A, B):`. A file that still does not parse is a file gap.
- Name reads join their bindings flow-insensitively within a function. A read with more than one reaching binding is `partial`.
- A Python route opens its handler in anchor mode. `routeGraph` has no Python meaning.

## Python rules

- Any `def` or class anchors by name (#164). Calls pair by invocation (#166).
- Classes flow through fields and annotations (#172). ORM models get fields from assigned field instances (#189).
- External-code and branch-test ends apply to Python (#177). A request starts at the request and its response ends at the return (#181). Values begin and end where the code does (#199).
- A framework decorator's function is an entry (#185). A FastAPI dependency parameter fills from its function, and a function handed to outside code is entered (#204).
- Routes: a first-party subclass of `APIRouter`, `FastAPI`, `Flask` or `Blueprint` is a router; a mount prefix carries through every router above it and may be a settings field with a literal default (#221).
- A root that is itself a package names its modules from above it, so its own imports resolve (#221).
- A SQLAlchemy session write (`add`, `add_all`, `delete`, `merge`, and the async session's) ends a trace as a database write (#222).
- A value handed to library code with no model is assumed to reach its result, so a trace that lands only through it is partial; a built-in type's or a standard container protocol's method is modelled (#223).
- A first-party Celery task's `delay(…)` and `apply_async(args=…, kwargs=…)` bind its parameters like a call, so a task's inputs trace back to every place that queues it, and a queued value walks into the task. The call's result is the task's handle, never its return.
- A file or folder anchor lists a Python module's public top-level functions and classes as its exports, each one opening into its trace.

- Catalog: `engine/examples/pattern-catalog/python` holds 75 everyday Python patterns (plain Python, boundaries, FastAPI, Flask, Django, DRF, SQLAlchemy, Celery, click, pandas). The first run reached 44 wanted ends, the run after the rules below reached 64 (60 `ok`), and the scope and callable rules at the end of this list bring it to 75 `ok`, every one at its wanted end.
- A `yield` or `yield from` leaves a generator as a return does, and the yield of a `@contextmanager` function reaches the `with ... as` name.
- An argument to a network, database or subprocess call ends at the call as an external effect.
- A method call finds its library row through the class its receiver was built from or annotated with, or through a library base class of a first-party class. The packages do not need to be installed. New rows cover argparse, SQLAlchemy and SQLModel `Session`, pandas, Django and DRF `Response`.
- In `x = f(x)`, the read on the right sees the earlier `x`.
- `global X` binds and reads the module's `X`; `nonlocal X` the nearest enclosing function's. Loads join their bindings after every body of the module is walked, so the order of the functions does not matter.
- Module state: a write to a module name's constant key or attribute (`CURRENT["theme"] = theme`) can be what any read of that key in the module sees (partial, flow-insensitive). A read of another key is not joined.
- A function returned as a value (`return apply`) goes to the caller of the function that returns it. When that function is an entry (nothing calls, holds, decorates or registers it), the closure's returns leave the program as `return`. Returned by a function the program calls, the closure escapes, and its return stays an unproven hand-off.
- A call of a local `def` enters it. `to_ops = functools.partial(send, "ops")` bound once makes `to_ops(x)` a call of `send` with `"ops"` first.
- `f(*items)` and `f(**options)` fill the parameters that nothing else binds: proven for a parameter with no default, partial otherwise.
- A `match` capture binds from the subject: `case x` the subject itself, a capture inside a sequence, mapping or class pattern an element of it.
- A library call that calls the function it is given (`FORWARDING_CALLS`: `BackgroundTasks.add_task`, `Executor.submit`, `asyncio.to_thread`) binds that function's parameters from the arguments after it. `submit` and `to_thread` also return the function's return (`submit` in a future, whose `result()` is a `passes-through` row).
- A call of a parameter (`fn(item)`) is a call of the function every call site passes for it, when they all pass the same one and nothing else holds the function. A library function with a terminal row (`print`) makes the call that terminal. Call sites that pass different functions leave it external.
- A method's row is also looked up by the receiver's own class: `handle.write` on an `open(..., "w")` handle is `_io.TextIOWrapper.write` (a file write), while mypy names the shared base `_io._TextIOBase.write`, which a `StringIO` has too.
- A field or key written on a local name before that name is handed to a sending terminal (`article.title = …` then `article.save()`, `row["k"] = …` then `print(row)`) goes with it. A Django manager's `get`, `create`, `first` or `last` names an instance of its model.
- `passes-through` rows (Flask's `request.*`, DRF's `is_valid`, `asyncio.gather`) and a query result's methods after a database origin (`.scalars()`, `.all()`) are modelled: their result derives from their receiver and arguments, so a trace through them is `ok`, not `assumed`.
- A dependency that FastAPI calls for a route (`Depends(f)` on a handler, or on such a dependency) fills a parameter with an explicit marker (`Header()`, `Query()`, …) or a `Request` annotation from the request, proven. Its other parameters stay assumed.

## Engine structure

- Design rules, decisions, measurements and the batch evidence behind reports and the treemap (`fileSignals`): `docs/dataflow-engine.md`.
- Function effects follow bounded local `const` alias chains for modeled receiver mutations. A write through an unchanged parameter is reported; a fresh array literal or built-in array slice is not an outside write. When ownership cannot be determined (for example through a mutable alias or a field on a local object), the result names that gap instead of reporting the function as closed.
- `flowSignature` reduces each function of a file to line-free keys (origins, ends, origin→end pairs, parameter reads, effects, stops, status). `srcly compare --dataflow` diffs them as "Data-flow changes". Python has no parameter reads or effects (not measured), and a caller of a changed function is not re-traced.

- Every evidence kind is classified once in `engine/src/srcly/kinds.ts` (#200). Rules read traits, not lists of kind names.
- Library models load as data rows (#206). Python origins and terminals read from rows (#212). The rules are in `docs/dataflow-engine.md` (Library models); the 2026-11 migration is in `docs/research/dataflow-library-models-2026-11/README.md`.
- No list of framework names is left in the engine (migration stage 7). A call into a package is a framework call when a row names it, and an assumed effect otherwise. Rows carry the labels: a binding's `state` (signal, store, resource, memo, context), a handed function's scope role (`scopes`: `createResource`'s fetcher, `query(fn)`'s server function, any object's `queryFn` and `mutationFn`), and a URL read (`input: "url"`: `useParams`, `useSearchParams`, `useLocation`, `usePathname`, `useSearch` in Solid Router, React Router, Next and TanStack Router). A scope role and a state label now need the callee to resolve to that package; a user function named `query` is no longer a server function.
- Memory: the engine holds one Program and bounds what it keeps (#165). The checker truncates the type text in facts (#193).
