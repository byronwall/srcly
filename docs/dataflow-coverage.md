# Data-flow coverage: what landed

This file records the data-flow coverage work that is in `main`. Open work is in the backlog grid (`pgm/data`, see `AGENTS.md` → Backlog), not here.

The work came from the data-flow experience audit (October 2026). The audit traced about 120 exports per repo on six repos and ranked where traces stop. Each PR below removes one cause of a false stop, or names a stop that was silent.

## How coverage is measured

- `engine/scripts/survey-blockers.ts` traces a sample of exports in both directions and writes every outcome and stop as JSON (#162). `engine/scripts/survey-report.ts` ranks the stops.
- `pnpm survey-gate` (CI's `survey` job) surveys `client/`, `server/` and `examples/value-flow-basics` and fails on any move the PR does not record (#192, #205).
- A rule's test is an annotated fixture in `engine/examples/value-flow-basics/src/`. `engine/test/srcly/fixture-annotations.test.ts` checks the `@trace`, `@outcome`, `@reaches` and `@stop` claims (#201). `@path` and `@no-path` name a route between two labelled boxes, so a wrong route to a legal end fails. `engine/examples/value-flow-js/` runs the same claims on actual `.js` files, after a check that each file is in the Program.
- The r3 survey, before #198, was 19% ok: TypeScript 16%, Python 25%.

## Outcomes and honesty

- A trace says what each side holds and where it stops (#151, #152, #155). A frontier box is labelled by why the trace stops (#158), and every partial trace names its stop (#169).
- `ok` means proven. A trace that lands only through an assumed library step is not `ok` (#183).
- Every relation between two boxes is kept as its own edge (its kind, field and proof), and the view draws them as one edge that lists them all at the strongest status. A field edge is named by the field it moves, whichever way the walk came. A pair of boxes is assumed only when every edge joining them is. The ledger takes the same `assumed` rule (`assumedCallee`), so `slugify(props.title)` reads `assumed` in both views. Before, the first relation the walk met named the edge and the rest were lost: on srcly's own client, 3,509 dropped relations differed from the one kept (2,051 lost a field name, 1,069 a second relation kind such as `consumer-value`).
- A return of a function that no call names, only handed on as a value (a callback, a nested `def` passed to a runner), is an unproven hand-off, not where the value leaves: the trace is `partial` and names it. The Python helper counts a nested function read as a value as escaping.
- A function anchored by name walks its body forward: each parameter reaches the function's writes, calls and returns, so a handler shows what it does with its input and reads `partial` when its body stops inside. Before, it walked only returns and uses, and `create_item` read `ok` with its database write off screen.
- A budget-exhausted route slice names its omission (#161). Size limits are spent only on fields the trace reads and places it draws (#168, #197).
- When nothing is drawn, the view says why and offers to try again (#160).
- A trace over 40 boxes opens folded: the anchor's own function in full, each other function as one box with its file, step count and ends ("reaches database write, response"). A box opens in place. `User.email` forward went from 62 boxes to 11, `SECRET_KEY` both ways from 177 to 33.

## TypeScript rules

- Dead ends: four kinds carried past (#167); four more found by fixture annotations (#202). Backward, a parameter of a function handed to a package (`handleSubmit((values) => …)`) begins in that package, as an external import does. Backward, an empty `{}` or `[]` is where a value begins, as a literal is.
- Reads and writes: a read sees every assignment that can reach it (#173); a compound assignment to a field (`ref.current += step`) writes its right side into the field, as `=` does; a computed key is a partial read of its receiver (#171); a computed key in an object literal (`{ [row.k]: v }`) picks a field and ends there, as `obj[k]` does; array elements, spreads and `for…of` (#174).
- Calls: the slice's call pairing is trusted at every helper (#170); a function's field reads land through its argument (#163); a first-party method is entered through `this` (#176); `new X(…)` and `super(…)` enter the constructor the checker resolves, a parameter property (`constructor(public label)`) writes its member, and a getter's returns are what a read of its member sees; a generator's `yield x` reaches the loop over its call; a call is paired with the one function its value is, through objects, bindings and aliases (#198, `engine/src/analysis/value-origin.ts`). A call through a function-typed parameter or prop (`visit(item)`, `props.onSave(v)`) enters each function a caller hands in, paired with the call or occurrence that handed it in, so two callers' handlers never cross (`bound-handler`). A setter handed in (`onPick={setPicked}`) writes its state, a context method (`store.save(x)` after `useContext`, or a destructured `{ save }`) runs the provider's function, and so does a context whose value is itself the function (`const dispatch = useContext(Dispatch)`), a backward trace out of a handler leaves only through the caller that handed it in, and an arrow whose body is a void call returns nothing to its call.
- Library calls: a discarded call's arguments stay in a receiver its function declares (#175), and in a closure's variable, a parameter, or an element of one (`groups[key].push(row)`); in module state only when the module's own unexported container is read back in its file (`cache.set(k, v)` reaches `cache.get(k)`), never a write-only log or state shared across files; the write lands in the field the receiver names (`section.rows.push(row)` reaches `section.rows`, not `section.title`), and a push written as a void callback's body (`forEach((x) => rows.push(x))`) is a write; a library call's receiver reaches the function it is given (#184); a call made for its effect through a function a library hands back under a local name (`navigate(url)` after `useNavigate()`, `setSearch(…)`, `refetch()`) is an assumed external effect, resolved through the checker's signature, never a dead end; calling a function held in a field (`props.onPick(x)`) does not write `x` into the object; a library call is known by its import's module and export name (#209). A read through a namespace import (`api.greeting` after `import * as api`) reads the export itself. A wrapper call (`action(fn)`, `useCallback(fn)`) returns the function, so what the function returns reaches the wrapper's call sites, never the wrapper call itself.
- Call results: a React effect's call has no value, so what its callback returns (a cleanup) is not the hook's result, and generic callback handling cannot restore it (`returns: "void"`). `mutation.mutate(x)` and `mutateAsync(x)` enter their `mutationFn` as a call enters a function of the project's, so two calls on one hook stay apart and a payload the function drops reaches no result. Only `mutateAsync` hands the return back.
- Query results: a query's result is an object of fields, and only `data` holds the fetched value: what `queryFn` returns, or what `select` returns when the options have one. `select` takes what `queryFn` returns, so a field it does not read stops at its parameter. `status`, `error`, `isLoading` and the other fields never hold it. A mutation's `data` is what its `mutationFn` returns; `mutate` still has no value. A row's `field` and `selector` say this (`engine/models/react.json`). A destructured result (`const { data, isPending } = useQuery(…)`) still carries the value into every name, and `useInfiniteQuery` keeps the whole-value rule.
- Solid resources: `createResource(fetcher, options?)` has no source and `createResource(source, fetcher, options?)` has one, read per call (`resourceFlow`). The fetcher's return, inline or named, is the resource's value, and `initialValue` reaches it too. The source fills the fetcher's parameter and never reaches the resource by itself, so a source the fetcher ignores stops at the source. A `.json()` call the fetcher only reads does not reach the resource: the exact carrier needs the fetcher to return that value, through an `await` or a const binding, and a reshaped body goes by its fields.
- Solid results: `createEffect`, `createRenderEffect`, `createComputed` and `onMount` have no value. `onCleanup` returns the function it is given. `on` returns a new function, and its callback's return reaches a call of that function, never the `on` call. A selector's call is a boolean test of its source. `batch` and `untrack` still yield what their callback returns. Renamed imports (`createSignal as signal`) match the same rows. `const x = call(fn)` no longer makes `x()` a call of `fn` when a row says the call makes something else.
- Solid render callbacks: `<For each>` hands its callback (inline or named) each item as a value, and `<Index each>` hands it each item as an accessor, so `row.name` and `name()` both read the item. The second parameter (`For`'s index accessor, `Index`'s index number) is not fed from the list, and `each` is not a DOM attribute. `<Show when>` hands its value as an accessor, or as the value itself when `keyed`. Fixture `engine/examples/value-flow-basics/src/solid-render-callbacks.tsx`.
- Loose projects: a jsconfig or tsconfig with `strictNullChecks` off is analyzed, and so is a folder of JavaScript or TypeScript with no config, whose options the engine infers in memory (it writes nothing to the project). Every result says `nullProof: false`, and an empty `tsconfig` when there is no config, and the rail reads "No null proof". A trace holds the same way, but no rule may read `undefined` from a type there: `mergeProps` only trusts a later literal. A broken config is still refused by name. The `tsx-dataflow` report still needs a real config, because its nullish verdicts read those types.
- Promises: a promise's outcomes are separate channels, read from `settles` rows in `engine/models/ecmascript.json`. A fulfilled value reaches the first callback of `then` and never a rejection handler. `then` holds what its callbacks return, not its receiver. `catch` keeps the fulfilled value and adds what its callback returns (recovery). `finally` keeps the fulfilled value, its callback takes nothing, and what the callback returns ends there. A named handler (`.then(show)`) is entered as a written one is. `Promise.reject(reason)` holds no value: the reason reaches a `catch` or a second `then` callback, over any `then` or `finally` between them, and with no handler in sight it ends there as a thrown value does. `reject(reason)` in `new Promise` ends there too, and only `resolve` hands a value back. A rejection from a `throw` or from a promise the code does not show is not traced, so the handler's parameter starts there.
- Native writes: whether a standard method changes its receiver comes from its row in `engine/models/ecmascript.json`, not from the caller dropping its value. `const n = rows.push(row)` keeps `row` in `rows`, and a dropped `rows.concat(row)` keeps nothing and ends there. A method of the project's own with the same name keeps its own meaning.
- Native callbacks: an `Array` method's row in `engine/models/ecmascript.json` names what each callback parameter takes (`parameters`). `map`'s `index` takes a position, never an element; `reduce`'s accumulator takes the seed and then the callback's own last return. The callback's return reaches the call's value only for `map`, `flatMap` and `reduce` (`returns: "callback"`): `forEach` drops it, and `filter`, `find`, `some`, `every` and `sort` only test or order with it, so it ends at that callback's return.
- Receivers and keys: `bag["x"] = v` packs `v` under `x`, as `bag.x = v` does, and a read of `bag["y"]` takes only field `y`. A computed key (`bag[key] = v`) packs into some field, a `partial` step every read of `bag` may see. Assigning a setter the project declares (`cell.current = v`) runs it: `v` binds its parameter and `cell` its `this`. A member's state is still the class's, not one instance's.
- Call adapters: `f.call(t, a, b)`, `f.apply(t, [a, b])` (a list written out) and a call of what `f.bind(t, a)` returned run `f`, with `t` as its `this` and the arguments shifted into place, so an argument `f` drops reaches nothing. A value bound ahead (`this` or a leading argument of `bind`) enters `f`, but its return is not paired back to the later call: it stops at `unproven-handoff`.
- Contexts: `useContext(Ctx)` gets the value of the nearest `Ctx` provider above the reader, or the `createContext` default where no provider is above it (`engine/src/analysis/program-evidence-context-ancestry.ts`). The walk goes out from the reader to its component or hook, and out from each place that one is rendered or called. A provider whose subtree has no reader supplies nothing. React 19's `<Ctx value>` is a provider too, never a DOM attribute or a component. The context object is not the value read. Where a mount is not known (an exported component nothing renders, a component handed on as a value, a render prop, a component that renders its own provider around children), every provider outside the components walked through, and the default, are candidates. A hook's one `useContext` call serves every caller, so each caller gets every value any caller may get.
- Reducers: a dispatch reached through a prop or a context runs the reducer as a direct one does. It used to write its argument straight into the state, so a reducer that ignores its action still showed the action in the render. A function given to a dispatch is an action: nothing calls it.
- DOM reads: a dropped `querySelector`, `closest` or `getAttribute` call is a read, not a page write. `engine/models/web.json` names the finite list. A DOM method it does not name keeps the old rule, and a project's own `querySelector` was never the page.
- Result cache: the engine fingerprint covers the library model rows, so a changed row misses the cache in a checkout and in a bundle.
- Components: prop reads in closures and string-literal props bind to the caller (#159); destructured and optional props bind (#186); a prop binds to a field read of a view of the props (a `const` copy, or what a `passes-through` row returns: `mergeProps(defaults, props)`, both halves of `splitProps`), when the view holds that field: each half of `splitProps` holds its own keys, `mergeProps` takes a field from the last source that sets it, and a key list the code computes or a later value that may be undefined keeps the prop; `mergeProps` keeps a field through the call, so a default for `kind` never reaches `merged.other`; a factory or alias component renders at the JSX tag that names it (#180); a default-exported function anchors by its own name (#178).
- State: a zustand store (a `store` row) holds what its function returns and what its `set` receives; a selector reads the field it names, and calling a member read through the hook (`setCount` after `useStore((s) => s.setCount)`) runs the store's function, never the selector it is written beside. a setter's value reaches its getter's reads (#182); a function handed to a setter (`setCount((c) => c + step)`, a store path's `setState("todos", (list) => […])`) stands for what it returns, and its parameter is the current state; a Solid store path (`setStore("left", "title", v)`) writes `left.title` alone, so a sibling field never sees it, an updater there (inline or named) receives that field, not the whole store, and a predicate in the path (`(item) => item.id === id`) is a test, never stored; a store or signal's initial value seeds it field by field, so `createStore({ left, right })` keeps `left` and `right` apart; a state-pair row marked `lazy` (React's `useState`) calls a function initial value, and Solid's `createSignal` holds it; a `useReducer` dispatch binds the reducer's action, and the reducer's return is the state; state-pair factory and getter calls are framework-modelled (#188), modelled in the collector (#196).
- Ends: a binding every read of which decides a branch (`if (forgotten)` in nested branches, `ready && <X />`, `<Show when={isVisible()}>`, through `!` or an accessor's call) ends at its binding, decides a branch. A parameter or local binding the program never reads (`_level`, `const { isSuccess } = useQuery()`) ends there, named "never read": the checker proves the value goes nowhere, so the trace is `ok`, not a dead end; the value-flow ledger draws every in-place end (a branch test, a write, never read) as a terminal row, as the graph does. A service write or read is a method on a client's contract, or a function-valued field a declaration file declares (a generated client's); a callback prop the project declares (`props.save(x)`) is never one. A thrown value ends at the throw (#207). An exported value that nothing in the program reads ends at its export, the module's API, not at a dead end; a call through a callback an export nothing in the program calls was handed (`onSeen(id)`, `props.onPick(x)` in a component nothing renders) ends there too, at the module's API, never a library method on a parameter (`items.forEach`); one the program reads, by name or through `import * as`, walks on to that read. A function handed to a timer (`setTimeout`, `requestAnimationFrame`) ends there: the callback runs later. A function handed to a page element as a handler (`<button onClick={click}>`) is not an escape: the page drops what it returns. A trace whose anchor has nothing beyond it names a stop at the anchor. A context `Provider`'s `value` goes to its readers, never into the page. A request ends a forward trace where it is sent, and a backward trace lands at the request a response came from: neither stops at the response body. A promise chain the code drops (`load().then(show);`) ends there. A function library code hands to a callback (`resolve` in `new Promise((resolve) => …)`) hands its argument back to the call that supplied it: the value reaches that call's value, and the call through it ends there, handed back. A DOM call the code makes for its effect (`el.classList.add(x);`, `target.dispatchEvent(e);`, `() => input?.focus()`) is a page write: any member TypeScript's DOM lib declares, whose value the code drops. A DOM call whose value the code uses (`root.querySelector(sel)`) carries on. An arrow whose body is an optional void call returns nothing. `response.json()` on a `fetch` result reads the body; only a server's response is an HTTP response. An emitter's `emit("name", x)` binds each listener its receiver registered with `on("name", fn)`, and `yield* list` hands on `list`'s elements. A return that is a call (`yield items.slice(…)`, an arrow's `() => f(x)`) is judged by its own function's call sites, never the call's, so an exported generator no code iterates ends at its return. A class's annotated uses fold by file (#208). A `when` on Solid's `Show` or `Match` ends as "decides a branch", not a DOM attribute.

## Symbol view of an anchor trace

The symbol view is the default drawing of an anchor trace. `?model=steps` (the Steps toggle in `FlowTools.tsx`) keeps the old one-box-per-step view.

- One box per symbol. Boxes merge by scope and checker symbol id, which the anchor-graph contract carries as `symbol` and `field`, never by label. A node with no symbol keeps its own box. A merged edge keeps every original proof. On visual-notes' DocView this cut 557 boxes to 225.
- The anchor-graph contract is the one seam: `engine/src/srcly/contracts/anchor-graph.ts` feeds `client/src/viz/deps/flow/anchorAdapter.ts`. Each fact the view needs (symbol, operation, `symbolKind`, frame `role`, links) is an additive field on it.
- Value flow is the bold main line, with its operation named on the edge. Calls, reads and writes are thin links that can be toggled.
- `symbolKind` (state, transform, origin, end, plain) carries the strong color. Frames stay neutral and name their role: component, hook, helper, handler, fetcher, server or unknown. Roles live in `engine/src/srcly/scope-roles.ts`, never in `engine/src/analysis`. Unknown is never drawn as a component.
- The first screen is the main path from origins to ends. Side branches are stubs that grow with `+` and `−` or the depth control (1, 2, 3, all) in `depth.ts`. Depth is in the URL and the view-state registry.
- Plain TypeScript modules with no routes or components are an equal target.
- Tune the view on `engine/examples/symbol-graph/`. Use a large app such as visual-notes to check scale and find engine errors.

## Python type source

A Python root uses the same engine contracts as TypeScript. `engine/python/srcly_pyfacts.py` provides the evidence. The engine runs it once per generation.

- Structure comes from the standard library's `ast`. Types and call targets come from mypy's `build.build` with `export_types`. The helper prints ProgramElement and ProgramRelation facts in the collector's raw shape.
- A box's type is mypy's type at that span (`typeSource: "mypy"`). Where mypy has none, such as a parameter or a file it could not check, the annotation text stands in (`typeSource: "annotation"`). A pydantic or dataclass field read cites the field's declaration as proof.
- mypy names the function or method a call reaches (`CallableType.definition`). This gives argument-to-parameter and return-to-call relations without guessing.
- mypy reads the project's own packages through `python_executable`: the project's `.venv`, else `VIRTUAL_ENV`, else the helper's interpreter. mypy is a dependency of srcly's server. When mypy is missing, the engine refuses with `python-checker-not-found`.
- Rejected: annotations over `ast` alone (would need a hand-written inference engine for unannotated code), `pyright --outputjson` (diagnostics only, no types) and pyright's language server (one hover at a time, about 65 s for `server/app`, display strings with no call structure).
- Measured on 2026-10-24 on srcly's `server/` (59 files): 4.9 s wall, of which mypy took 2.3 s, and 563 MB peak RSS. mypy typed 91% of expressions precisely.
- Origin and terminal roles come from each element's `kind`, so new Python recognition goes in the helper's tables and in the `py` rows of `engine/models/python.json`, never in `engine/src/analysis`.
- A file with syntax newer than the helper's interpreter is rewritten when an older spelling keeps every column: `except A, B:` (PEP 758) becomes `except(A, B):`. A file that still does not parse is a file gap.
- Name reads join their bindings flow-insensitively within a function. A read with more than one reaching binding is `partial`.
- A Python route opens its handler in anchor mode. `routeGraph` has no Python meaning.

## Python rules

- Any `def` or class anchors by name (#164). Calls pair by invocation (#166).
- Classes flow through fields and annotations (#172). ORM models get fields from assigned field instances (#189).
- External-code and branch-test ends apply to Python (#177). A request starts at the request and its response ends at the return (#181). Values begin and end where the code does (#199).
- A framework decorator's function is an entry (#185). A FastAPI dependency parameter fills from its function, and a function handed to outside code is entered (#204).
- Routes: a first-party subclass of `APIRouter`, `FastAPI`, `Flask` or `Blueprint` is a router; a mount prefix carries through every router above it and may be a settings field with a literal default (#221).
- A root that is itself a package names its modules from above it, so its own imports resolve (#221).
- A SQLAlchemy session write (`add`, `add_all`, `delete`, `merge`, and the async session's) ends a trace as a database write (#222).
- A value handed to library code with no model is assumed to reach its result, so a trace that lands only through it is partial; a built-in type's or a standard container protocol's method is modelled (#223).
- A first-party Celery task's `delay(…)` and `apply_async(args=…, kwargs=…)` bind its parameters like a call, so a task's inputs trace back to every place that queues it, and a queued value walks into the task. The call's result is the task's handle, never its return.
- A file or folder anchor lists a Python module's public top-level functions and classes as its exports, each one opening into its trace.

## Engine structure

- Every evidence kind is classified once in `engine/src/srcly/kinds.ts` (#200). Rules read traits, not lists of kind names.
- Library models load as data rows (#206). Python origins and terminals read from rows (#212). The plan and its progress are in `docs/intent/dataflow-library-models/plan.md`.
- Memory: the engine holds one Program and bounds what it keeps (#165). The checker truncates the type text in facts (#193).
